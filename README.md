Цей проєкт виконано в межах домашнього завдання №5 з курсу з реляційних баз даних та SQL. ## 📋 Що було виконано впродовж роботи (`hw_05.ipynb`)

### 1. Setup та Typed-схема Olist
* Завантажено сирі дані електронної комерції Olist (`olist_customers_dataset.csv`, `olist_orders_dataset.csv`, `olist_order_items_dataset.csv`, `olist_products_dataset.csv`, `olist_sellers_dataset.csv`).
* Створено сувору реляційну схему з використанням первинних (`PRIMARY KEY`) та зовнішніх (`FOREIGN KEY`) ключів, обмежень (`CHECK` для статусів замовлень, цін та розмірів), а також оброблено особливості сирих даних (наприклад, виправлено одруку в назвах колонок довжини товарів).

### 2. Feature Engineering Pipeline через CTE (≥5 stages)
Побудовано багаторівневий пайплайн розрахунку клієнтських ознак за допомогою зв'язаних Common Table Expressions (CTE):
* **`reference_date` (Stage 0):** Фіксація стабільної опорної дати (`MAX(order_purchase_timestamp)::DATE + 1`) для уникнення залежності від поточного дня.
* **`stage1_orders_total` (Stage 1):** Розрахунок загальної вартості кожного замовлення (сума ціни товарів та вартості доставки з урахуванням `COALESCE`).
* **`stage2_rfm` (Stage 2):** Обчислення класичних RFM-ознак для кожного клієнта (`recency_days`, `frequency`, `monetary`, `first_order_date`).
* **`stage3_cohort` (Stage 3):** Визначення когорти клієнта за кварталом першої покупки (`cohort_quarter`).
* **`stage4_rolling_aov` (Stage 4):** Обчислення ковзного середнього чека за останні 30 днів (`avg_order_value_30d`) із застосуванням віконних функцій (`WINDOW`).
* **`stage5_cancel_rate` (Stage 5):** Розрахунок частки скасованих замовлень по кожному клієнту (`cancellation_rate`).
* **`stage6 & stage7` (Stages 6–7):** Визначення улюбленої категорії товару (`preferred_category`) на основі ранжування виручки за категоріями (`ROW_NUMBER()`).

### 3. Рекурсивний CTE для побудови мережі рефералів
* Створено синтетичну таблицю `hw5_referrals` для зв'язків типу «запросив → запрошений».
* Реалізовано рекурсивний запит (`WITH RECURSIVE referral_depth`) для обчислення глибини зв'язків та формування шляхів (`path_text`).
* **Захист від циклів:** Застосовано масив відвіданих ідентифікаторів `path_ids` із перевіркою `NOT r.referred_customer_id = ANY(rd.path_ids)` та обмеження глибини (`depth guard`, наприклад, `rd.depth < 50`), що гарантує захист від зависання у випадку циклічних графів ($A \to B \to A$).

### 4. Кешування через Materialized View з `CONCURRENT REFRESH`
* Повний CTE-pipeline обернено у Materialized View `mv_olist_customer_features`.
* Створено обов'язковий унікальний індекс за `customer_id` (`UNIQUE INDEX`), що дозволило виконати асинхронне оновлення кешу без блокування читання (`REFRESH MATERIALIZED VIEW CONCURRENTLY`).

### 5. Бенчмаркінг через `EXPLAIN ANALYZE` та порівняння планів
Проведено порівняльний аналіз продуктивності:
* **Повний CTE-pipeline:** Виконання важких агрегацій займає більше часу (`~819 ms`), основне навантаження припадає на вузол **`HashAggregate`** та сортування з використанням тимчасових файлів на диску (`temp read/written`).
* **Lookup із Materialized View:** Завдяки унікальному індексу запит виконується миттєво (`~0.11 ms`) через **`Index Scan`**.
* **Сортування за `monetary` (з додатковим індексом):** Створено індекс за спаданням виручки (`monetary DESC`), що дозволило ефективно виконувати масові вибірки топ-клієнтів із залученням паралельних воркерів (`Gather Merge`) у пам'яті без запису на диск.

## 💡 Висновки (Reflection)

1. **Найдорожча операція у пайплайні:** Це **`HashAggregate`** та наступне сортування (**`Sort`** / `top-N heapsort`), оскільки базі даних доводиться групувати великі масиви даних поєднаних таблиць і формувати тимчасові файли на диску.
2. **Доцільність Materialized View та цикл оновлення:** Кешування життєво необхідне для складних ML-пайплайнів. Оскільки дані електронної комерції оновлюються ретроспективно, оптимальним вибором є **щодобовий (daily) оновлюваний цикл** у години найменшого навантаження (`REFRESH MATERIALIZED VIEW CONCURRENTLY`).
3. **Коли використовувати звичайний VIEW:** Звичайний `VIEW` краще застосовувати, коли критично важлива абсолютна актуальність даних у реальному часі (**real-time freshness**), а базові таблиці змінюються невеликими порціями.
4. **Termination рекурсивних запитів:** Рекурсія зупиняється автоматично, коли anchor/recursive частини не повертають нових рядків. Графові цикли на кшталт $A \to B \to A$ блокуються за допомогою перевірки `ANY(path_ids)` та `depth guard`.
5. **Головний Trade-off:** Головний компроміс полягає між свіжістю даних (**freshness**) та продуктивністю/латентністю (**latency / recompute-cost**). Пожертвувавши ідеальною реального часу актуальністю на користь щоденного кешу, ми отримуємо мікросекундний `Index Scan` замість важких щосекундних перерахунків.
